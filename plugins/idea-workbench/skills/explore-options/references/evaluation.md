# Option evaluation

Use this guide to compare solution directions without manufacturing certainty or favoring a preselected answer.

## Construct a fair option set

- Hold the desired outcome and boundaries constant across options.
- Make options differ in a consequential way: mechanism, ownership, boundary, dependency, reversibility, or risk.
- Include the current state, a smaller intervention, reuse, or integration only when it could honestly win.
- Describe every option at comparable depth. Do not give the preferred option a finished design while reducing the others to labels.
- Reject hybrids that merely accumulate the attractive parts and costs of every option. A hybrid must have a coherent governing idea.

## Derive evaluation criteria

Choose criteria that can change the decision. Common candidates include:

- fit with the desired outcome and user journey;
- fit with appetite, constraints, and non-goals;
- time to useful evidence or value;
- feasibility and dependency risk;
- security, privacy, safety, and compliance exposure;
- operating burden and maintainability;
- reversibility and migration cost.

Prioritize the criteria with the user when priorities imply a product or business tradeoff. Omit irrelevant criteria rather than treating every list item as mandatory.

## Handle evidence and uncertainty

- Record a sourced observation as a **fact**.
- Record an accepted but unproven planning premise as an **assumption**.
- Record a falsifiable belief with a possible test as a **hypothesis**.
- Record an explicit owned tradeoff as a **decision**.
- Record an unresolved issue and its investigation path as an **open question**.

Use `strong`, `mixed`, `weak`, or `unknown` when a compact rating helps, and pair every rating with a reason. Use numerical weights only when the user needs them and can defend the priorities; test whether small weight changes reverse the result.

For each option, expose the important risk, operating consequence, irreversible commitment, and cheapest useful validation. If a high-impact unknown could change the recommendation and can be answered cheaply, investigate it before choosing.

## Test the recommendation

A decision-ready recommendation must:

- compare credible options against the same decision frame;
- identify the criterion or tradeoff that actually decides the ranking;
- fit the stated appetite and boundaries;
- acknowledge its strongest disadvantage and the best argument for another option;
- distinguish evidence from inference;
- state what new evidence or changed constraint would reverse it;
- leave no decision-critical open question without an investigation path.

Keep the artifact `Draft` when the options solve different problems, a favored option rests on hidden assumptions, or a high-impact unknown makes the ranking unreliable. Set it to `Ready for decision` only when the user can make an informed choice. Set it to `Chosen` only after the user explicitly selects a direction.

Selection is the gate to detailed design. Recommendation alone is not approval.
