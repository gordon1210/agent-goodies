## Contract inventory

Identify every changed consumer-facing contract:

- exported function/type/module
- HTTP/RPC/GraphQL endpoint
- event/message schema
- database schema or persisted representation
- file format
- CLI flags, exit codes, stdout/stderr format
- environment/configuration keys and precedence
- plugin/tool protocol
- generated client/schema/code

Find consumers in the repository and deployment topology. Do not assume a symbol is private solely because it is not documented.

## Wire and API contracts

Check:

- required versus optional fields
- absent versus null versus zero/empty
- field names, casing, aliases, and types
- enum additions/removals and unknown-value behavior
- numeric precision and identifier representation
- date/time format and timezone
- pagination/cursor semantics
- ordering and determinism
- status codes, headers, content type, and error body
- default values and changed interpretation
- request validation stricter than existing clients can satisfy
- response fields removed or repurposed
- version negotiation and feature discovery

“Additive” changes can still break strict decoders, exhaustive switches, signatures, hashes, cache keys, or size limits.

## Events and asynchronous consumers

Check producer and all available consumer versions for:

- unknown field/value handling
- required field introduction
- semantic changes under the same field name
- partition/routing key changes
- ordering and deduplication identity
- retry/dead-letter behavior for new errors
- event emitted before state is committed
- replay of old events into new consumers
- new events consumed by old code during rollout

A schema registry pass does not prove semantic compatibility.

## Configuration and CLI contracts

Inspect:

- renamed/removed keys or flags
- changed defaults
- precedence changes
- boolean/list/duration parsing
- environment variable expansion
- unknown-key behavior
- config generated by older versions
- automation parsing stdout/stderr or exit codes
- non-interactive versus interactive behavior
- deprecation path and aliases

Configuration can be an external API even when only operators consume it.

## Database and stored-data contracts

Check:

- old rows/documents/files read by new code
- new rows written by new code read by old code
- nullable/default behavior
- enum/type/encoding changes
- indexes/constraints that reject existing data
- serialization version and migration marker
- partial backfill state
- rollback after new-format writes
- generated ORM/client code synchronized with schema

Do not assume all data is rewritten atomically during deploy.

## Rolling deployment

Build a compatibility matrix when versions coexist:

| Producer/Writer | Consumer/Reader | Must work? |
|---|---|---|
| old | old | baseline |
| old | new | usually during rollout |
| new | old | usually during rollout |
| new | new | target |

Also check rollback: after new code writes data, can old code resume safely?

Use repository evidence such as replicas, rolling strategy, independent services, queues, clients, and deployment scripts. Do not impose rolling compatibility on a proven atomic/offline upgrade.

## Error contracts

Check whether changes alter:

- retryable versus permanent classification
- status/exit code
- error type or machine-readable code
- partial result semantics
- idempotency/retry instructions
- redaction and user-visible detail
- wrapping that breaks caller matching
- success with warning versus failure

A friendlier message is not enough if automation relies on the original code/type.

## Verification

A finding should name:

- producer and consumer
- old/new version or representation combination
- exact changed field/default/error behavior
- consumer failure or wrong interpretation
- rollout or usage path proving coexistence
- available compatibility mechanism checked

Inspect generated clients, fixtures, contract tests, schemas, release scripts, and downstream packages in the repository.

## Severity calibration

- A likely production rollout outage or broad message-processing failure is High.
- A break affecting a supported but uncommon client is Medium.
- A documentation mismatch without runtime consequence is Low or not a code finding.
- Deterministic total outage during the standard critical-service rollout may be Critical only when containment and rollback are ineffective.
