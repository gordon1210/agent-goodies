# Documentation, Observability, and Operations

Read this reference for public APIs, comments, examples, command-line tools, services, background workers, configuration, telemetry, deployment behavior, health, lifecycle, source maps, and operational readiness.

Documentation and telemetry are product contracts. They must describe and expose actual behavior without leaking sensitive data or coupling users to unstable internals.

## 1. Documentation hierarchy

Keep each fact at the narrowest useful source of truth:

- Package/module docs: purpose, architecture, core invariants, runtime/platform requirements, and primary entry points.
- Public symbol docs: caller-visible semantics, input/output, errors, side effects, cancellation, units, complexity, and examples.
- README: installation, quick start, support matrix, common workflows, and links to deeper docs.
- Architecture/decision records: cross-cutting choices, alternatives, consequences, and migration constraints.
- Generated API docs: published surface derived from stable declarations and comments.
- Operations docs: configuration, deployment, health, recovery, migrations, alerts, and runbooks.
- Release notes/migration guides: user-visible changes, deprecations, compatibility windows, and rollback limits.

Do not duplicate volatile configuration/default/version details across many files. Link to one source of truth.

## 2. Public API documentation

Document what callers cannot infer reliably from the signature:

- Runtime validation and accepted formats.
- Preconditions, postconditions, and invariants.
- Missing/null/empty/default semantics.
- Units, ranges, normalization, encoding, timezone, ordering, and determinism.
- Error categories, thrown/rejected/result behavior, and retryability.
- Cancellation and timeout behavior.
- Side effects, persistence, idempotency, and atomicity.
- Ownership/lifecycle: subscriptions, streams, disposables, workers, handles, and cleanup.
- Module/runtime/browser/compiler availability.
- Complexity and resource limits when material.
- Examples for normal use and easy-to-misuse behavior.

Do not promise stronger stability, precision, timing, ordering, or compatibility than implementation and support policy provide.

### TSDoc/JSDoc

Follow repository tooling and syntax. Keep comments valid for the actual documentation generator and compiler generation.

Useful tags/sections may include:

- Parameters, returns, throws/errors.
- Examples.
- Remarks.
- Deprecation with replacement and timeline.
- Internal/alpha/beta status where publishing tooling honors it.
- Type parameter meaning when non-obvious.

Do not use documentation tags as enforcement if the compiler/runtime/tooling ignores them.

## 3. Examples

- Keep examples small, compilable, and representative of the public entry point.
- Use the package as a consumer would, not through monorepo source paths.
- Avoid secrets, production endpoints, personal data, and environment-specific assumptions.
- Show cleanup/cancellation when normal use requires it.
- Keep examples compatible with supported runtime, module, browser, and TypeScript versions.
- Test examples where practical.
- Distinguish pseudocode explicitly.

A stale example is worse than no example because users treat it as executable documentation.

## 4. Comments

Comments should explain:

- Why a non-obvious design exists.
- Which invariant makes code correct or secure.
- Why a workaround is required and the condition for removal.
- Why an apparently simpler alternative is invalid.
- The source of a protocol, algorithm, compatibility, or platform rule.
- Type assertion evidence when an unavoidable interop boundary requires it.

Do not:

- Narrate syntax.
- Restate names/types.
- Explain what old code did or justify a change relative to history.
- Mention that code was generated by an agent.
- Preserve outdated implementation detail.
- Add decorative section comments to tiny functions.

Use version control and decision records for history. Keep TODOs actionable with an owner/condition/reference.

## 5. Configuration design

Treat configuration as an external interface.

Define:

- Sources and precedence: defaults, files, environment, flags, remote config, per-tenant overrides.
- Build-time versus runtime values.
- Required versus optional and absent versus empty/zero/disabled.
- Type, unit, range, enum, path, URL, and secret semantics.
- Unknown-key behavior.
- Restart versus live-reload behavior.
- Backward compatibility and migration.
- Failure and fallback policy.

Rules:

- Parse and validate once at startup/reload/boundary into a typed internal configuration.
- Do not use assertions on `process.env` or equivalent to claim required values exist.
- Keep secure defaults and explicit opt-in for dangerous modes.
- Do not log secret values or entire config objects.
- Keep browser-public configuration on an explicit allowlist.
- Avoid a mutable process-global singleton when explicit ownership keeps tests and reload semantics clearer.
- If live reload fails, preserve or reject the old configuration according to an explicit atomic policy.

## 6. Command-line interfaces

A production CLI should behave predictably in automation:

- Stable exit status with documented meaning where callers depend on it.
- Diagnostics on stderr and machine-consumable output on stdout.
- No progress/decorative output in structured or piped modes.
- Explicit non-interactive behavior; never block unexpectedly for input.
- Clear precedence among flags, environment, config files, and defaults.
- Correct path, Unicode, shell, terminal, pipe, broken-pipe, and platform behavior.
- Bounded output and safe rendering of control characters/untrusted values.
- Atomic file output when partial writes are harmful.
- Signal/cancellation cleanup appropriate to the operation.
- Help text that explains semantics, defaults, units, and conflicts.
- Reproducible version output without network access.

Avoid secrets in command arguments when stdin, environment, protected files, or a secret provider is safer. Never build shell commands from CLI input unless the shell is explicitly the product boundary and escaping is rigorously defined.

## 7. Service lifecycle

A service needs explicit lifecycle semantics:

1. Parse and validate configuration.
2. Initialize required resources.
3. Verify schema/migration compatibility.
4. Start listeners/workers only when dependencies satisfy readiness policy.
5. Serve while emitting bounded useful telemetry.
6. Stop accepting new work during shutdown.
7. Drain/cancel/commit/roll back in-flight work according to deadlines.
8. Flush bounded critical telemetry/state where required.
9. Close servers, pools, streams, workers, and child processes.
10. Exit with meaningful status.

Startup must fail loudly for required invariants. Optional dependencies may degrade only when degraded behavior is intentional, documented, observable, and safe.

Do not hide startup failure behind endless retries unless the deployment contract explicitly prefers waiting and has bounded/observable behavior.

## 8. Health and readiness

Separate:

- **Liveness:** process/runtime is not irrecoverably wedged.
- **Readiness:** instance should receive new work.
- **Startup:** initialization remains in progress, where platform supports it.
- **Dependency health:** diagnostic state, not automatically liveness.

Guidance:

- Do not make liveness depend on every remote dependency; transient failure can create restart storms.
- Readiness may depend on resources required to serve correctly, but checks must be cheap and bounded.
- Avoid leaking internal topology, raw errors, credentials, versions useful to attackers, or customer data.
- Define behavior during draining, migrations, warmup, overload, and degraded mode.
- Instrument failures without high-cardinality labels.

## 9. Structured logging

Use structured events for operational behavior.

Each event should have:

- Stable event name/category.
- Severity tied to operator actionability.
- Safe bounded identifiers.
- Request/job/transaction context where appropriate.
- Error classification and causal information.
- No secrets or unnecessary payloads.

Severity guidance:

- **Error:** an operation failed or invariant was violated with service/user/operator impact.
- **Warning:** unexpected degradation, recovery, suspicious behavior, or approaching limit that may require action.
- **Info:** meaningful lifecycle/business-operational transition, not every detail.
- **Debug/trace:** diagnostic detail disabled or sampled in normal production.

Do not log the same error at every layer. Add context while propagating and emit once at the boundary that owns reporting.

## 10. Log safety

- Redact credentials, authorization headers, cookies, session/token values, signed URLs, private keys, personal data, and raw bodies by default.
- Bound strings, arrays, object depth, and serialized errors.
- Avoid serializing whole request, response, environment, config, database entity, or third-party SDK object.
- Prevent control-character/terminal/log-structure injection from untrusted values.
- Keep tenant data separated in access and storage.
- Define retention and access controls.
- Treat stack traces and source maps as potentially sensitive.
- Ensure logging cannot block critical work indefinitely or exhaust memory/disk under attack.

Custom error serializers should handle cycles, getters, proxies, thrown primitives, causes, and large fields safely.

## 11. Tracing and context propagation

- Create spans around meaningful operations, not every helper.
- Propagate context across promises, queues, streams, background jobs, workers, and RPC where supported.
- Record outcome and latency at the owning boundary.
- Keep attributes stable, bounded, and privacy-safe.
- Avoid raw URLs with user-controlled query strings, request/tenant IDs as metric dimensions, and large baggage.
- Ensure detached work deliberately inherits or severs request context.
- Do not use trace context as authorization evidence.
- Validate instrumentation against actual async/runtime behavior; custom callback bridges can lose context.

## 12. Metrics

Every metric needs a decision or diagnosis it supports.

Use:

- Counters for cumulative events.
- Gauges for current bounded state such as queue depth or active workers.
- Histograms for latency/size distributions with useful buckets.

Require:

- Stable name, unit, and semantic definition.
- Bounded label cardinality.
- Correct aggregation across instances/restarts.
- Clear owner and expected action.
- Sampling/aggregation behavior appropriate to scale.

Never use user IDs, request IDs, tenant names, full URLs, arbitrary paths, raw error messages, SQL, or unbounded strings as labels. Put high-cardinality diagnostics in controlled logs/traces.

## 13. Error reporting

Operational error reports should preserve:

- Top-level operation.
- Causal chain and safe stack/source location where permitted.
- Stable classification for alerting/retry/routing.
- Safe bounded context.
- Correlation identifier when detailed data lives elsewhere.
- Runtime/build version and deployment context where useful.

Avoid:

- Exposing debug objects directly to users or APIs.
- Turning every validation/user error into an operator alert.
- Alerting separately at every retry attempt.
- Hiding repeated failures behind silent fallback.
- Assuming every thrown value is an `Error`.

For browser reporting, scrub URLs, DOM text, form values, breadcrumbs, network bodies, and user data according to policy.

## 14. Source maps in operations

- Decide whether maps are public, private-uploaded, or unavailable in production.
- Preserve map chaining through all transforms.
- Prevent developer absolute paths and sensitive source content from leaking.
- Associate maps with immutable release/artifact identifiers.
- Test symbolication from a production artifact.
- Protect upload credentials and map access.
- Keep fallback diagnostics useful when symbolication is unavailable.

Do not publish inline source maps containing private source by accident.

## 15. Timeouts, retries, and resilience

- Propagate deadlines rather than stacking unrelated timeouts.
- Retry only transient failures and only when idempotent/unknown-outcome semantics permit it.
- Bound attempts, elapsed time, concurrency, queueing, and retained errors.
- Use backoff/jitter and prevent retry multiplication across layers.
- Honor trusted upstream retry guidance where appropriate.
- Expose exhaustion and degraded fallback through telemetry.
- Introduce circuit breakers, hedging, bulkheads, or fallback only for a demonstrated need with explicit state/lifecycle/testing.

Resilience mechanisms add complexity and can amplify outages if misconfigured.

## 16. Background jobs and queues

Document and observe:

- Delivery semantics and acknowledgement point.
- Idempotency/deduplication.
- Retry/backoff and dead-letter policy.
- Ordering/partitioning.
- Visibility timeout/lease renewal.
- Payload/schema version and limits.
- Concurrency and backpressure.
- Shutdown/draining.
- Tenant/security context.

Useful bounded telemetry includes queue depth/age, processing duration, outcomes, retry count, dead-letter count, and worker availability. Avoid exactly-once claims without an end-to-end proof.

## 17. Persistence and migrations

Operational documentation should cover:

- Schema/application compatibility.
- Migration order, expected duration, locks, and resource impact.
- Mixed-version rollout.
- Backfill progress and pause/resume.
- Backup/restore and rollback limits.
- Destructive cleanup timing.
- Failure recovery and operator decision points.

Migrations must be observable without logging sensitive rows. See [persistence-wire-contracts.md](persistence-wire-contracts.md) for design rules.

## 18. Deployment and configuration artifacts

- Keep image/package/serverless contents minimal and intentional.
- Record runtime and native-system dependencies.
- Use immutable artifact identifiers and reviewed provenance.
- Separate build secrets from runtime secrets and prevent both from entering layers/artifacts/logs.
- Verify configuration/environment schema at deployment startup.
- Define ports, files, permissions, writable paths, network dependencies, and resource limits.
- Test startup/readiness/shutdown in the deployed packaging model.
- Keep rollback compatible with schemas, messages, caches, and client assets.

## 19. Browser/front-end operations

Operational readiness for browser applications includes:

- Asset versioning and cache invalidation.
- Old client/new API compatibility.
- Chunk-load failure recovery after deployments.
- Source-map release association.
- Client error and performance telemetry with privacy controls.
- Service-worker update/rollback behavior.
- Feature-flag and configuration versioning.
- API timeout/retry/offline behavior.
- CSP/CORS and security headers in production.

Do not assume deployment is complete because HTML and bundles upload successfully; verify navigation, lazy chunks, hydration, API compatibility, and cache behavior.

## 20. Feature flags and emergency controls

- Define owner, default, scope, evaluation location, and expiry/removal plan.
- Do not use client-side flags to protect server authorization or secrets.
- Version flag semantics across old/new deployments.
- Avoid unbounded flag combinations and hidden permanent branches.
- Record safe values in telemetry without tenant/user high cardinality.
- Test both critical states and failure of the flag provider.
- Ensure emergency controls fail to a deliberate safe mode.
- Remove stale flags and code after rollout.

## 21. Alerts and SLOs

Alerts should correspond to user/operator impact and a concrete response.

- Base alerts on symptoms or reliable leading indicators.
- Include runbook and ownership.
- Avoid per-instance noise when aggregate service impact matters.
- Account for deploys, retries, queues, and expected traffic variation.
- Keep thresholds and windows tied to service objectives/resource limits.
- Test alerts or at least validate queries against known incidents/fixtures.
- Remove alerts no one can act on.

Dashboards should help answer a decision, not display every available metric.

## 22. Runbooks

A useful runbook contains:

- Trigger/symptoms and scope.
- Safe first checks with exact commands/queries where appropriate.
- Decision points and expected evidence.
- Containment and rollback actions.
- Data-integrity/security cautions.
- Recovery verification.
- Escalation criteria and ownership.
- Follow-up evidence to preserve.

Avoid vague advice such as “check logs” or “restart service” without conditions. Restarts can worsen corruption, retry storms, or evidence loss.

## 23. Deprecation and migration documentation

For user-visible deprecation:

- State what is deprecated and why.
- Provide a supported replacement with examples.
- State first-deprecated and planned-removal versions/dates when policy allows.
- Describe behavior/compatibility differences.
- Provide detection/codemod only when reliable.
- Keep runtime warnings bounded and non-sensitive.
- Do not remove before the documented compatibility window unless security requires it.

TypeScript compiler migrations need explicit configuration, declaration, tooling, and consumer notes—not only a dependency version change.

## 24. Operational review checklist

Before release, verify:

- User-facing and operator-facing behavior is documented.
- Configuration is validated, precedence is explicit, and secrets are protected.
- Logs, traces, metrics, source maps, and browser reporting are useful, bounded, and privacy-safe.
- Startup, readiness, liveness, draining, and shutdown are coherent.
- Async work, retries, timeouts, queues, and backpressure are bounded.
- Persisted/wire/client compatibility and migration behavior are understood.
- Failure paths are observable without duplicate noise.
- Automation receives stable output and exit status where promised.
- Deployment artifacts/configuration/provenance match the reviewed source.
- Runbooks and alerts cover failures requiring human action.
