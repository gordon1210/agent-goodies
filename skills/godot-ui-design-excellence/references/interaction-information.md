# Interaction and information: support the decision, not the database

## Map a short decision chain

For each screen, write: trigger → question → evidence → action → consequence →
recovery. Remove data that serves none of those steps unless it deliberately
provides atmosphere without competing with the task.

Separate frequent quick decisions from considered planning. A battle action list
and a buildcraft screen may expose the same ability through different information
hierarchies. Consistency means preserving its meaning, not forcing identical layout.

## Three useful disclosure levels

1. **Glance:** current condition and the next likely action.
2. **Inspect:** rationale, comparisons, costs, dependencies, and uncertainty.
3. **Commit:** the precise change and meaningful consequences.

These are project design levels, not universal latency targets. Keep critical
information visible when it becomes necessary. Do not hide a cost behind a hover
that appears only after confirmation. Progressive disclosure reduces simultaneous
complexity; it must not conceal basic discoverability.

## Favor recognition and stable context

Use persistent category names, recognizable symbols, consistent placement, and
state restoration. When returning from an inspector, restore the selected item
by stable identity, not only its previous row number. Sorting or filtering may
change positions while the user's object of interest remains the same.

A designer's Frostpunk 2 load-flow example moved useful save details to the
selection stage rather than revealing them only during loading. Generalize that:
comparison belongs before the irreversible or expensive commitment.

## Preview effects honestly

Separate current value, proposed value, delta, and assumptions. A projected
resource deficit is not an already incurred loss. Label estimates and time horizons.
Do not animate a preview into a permanent-looking success state before the game
has accepted the action.

For unavailable actions, show the reason near the action, with an actionable
explanation where possible. A gray button without explanation creates investigation
work. Consider whether inspection should remain reachable while activation is not.

## Recovery and throughput

Prefer a reversible action plus undo when appropriate; use explicit confirmation
for costly destructive changes that cannot be recovered. Do not put a confirmation
dialog on every routine action. Avoid forced holds as a universal safety pattern;
provide a practical alternative where the target audience needs it.

Measure work in meaningful tasks: find an item, compare two builds, identify why a
resource is falling, cancel a plan, return to the world. Record unnecessary steps,
wrong turns, and lost context. Counting beautiful screens is not usability evidence.
